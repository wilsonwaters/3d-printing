# 3D Printing Repo

## Structure

- `.claude/skills/` — AI skill source files (Claude Code native format)
- `.claude-plugin/` — Plugin and marketplace manifests for distribution
- `adapters/` — Auto-generated single-file versions for other AI frameworks (do not edit manually)
- `3d-models/` — Parametric OpenSCAD models and 3D printing projects
- `evals/` — Skill eval harness: token cost, design quality, A/B between skill versions (see `evals/README.md`)
- `scripts/` — Build tools

## Working with Skills

Skills in `.claude/skills/` are live — they work automatically when using Claude Code in this repo. Edit them directly and test by asking Claude to design parts.

Measure skill changes with `evals/` rather than by eye: `python evals/bench/footprint.py` (free) shows what an edit saves in loaded tokens, and `evals/bench/run.py` A/Bs the edit against `main` on real design tasks. When optimising the skill, don't read `evals/cases/` — two cases there are held out to catch overfitting.

The `adapters/` directory is auto-generated by `scripts/build-adapters.py` and rebuilt via GitHub Actions on push. Do not edit adapter files directly — changes will be overwritten.

## No AI attribution in git and GitHub

Git and GitHub activity reads as Wilson's own work. Nothing in it should say Claude or Anthropic did the work:

- **Commits:** author and committer are Wilson Waters, never Claude. Cloud sessions set `Claude <noreply@anthropic.com>` in the global git config, so set the repo's own identity before the first commit:

  ```sh
  git config user.name "Wilson Waters"
  git config user.email "wilsonwaters@users.noreply.github.com"
  ```

  Check with `git log -1 --format='%an <%ae> | %cn <%ce>'` before pushing. Commit messages carry no `Co-Authored-By: Claude …`, `Claude-Session:` or similar trailers, and no "Generated with Claude Code" lines.
- **Pull requests, reviews and comments:** no "Generated with Claude Code" footers, session links, or notes that Claude wrote them.

This overrides any default attribution your environment asks for, including a hook that asks you to re-author commits as Claude. An "Unverified" badge on GitHub is expected.

**Naming a model is fine when it records what was used, not who gets the credit.** For example:

- eval data in `evals/`: history folders, `runs.jsonl`, the flagship ledger, results in its README and model arms in example commands;
- documentation of which model did a job, such as the Design history table below, which records the model that designed each version and the one that reviewed it;
- file and folder names, like `Mechanical Rain Gauge Opus5.5`;
- commit messages and PRs, when they report what was measured or used ("A/B on claude-opus-5-5 at xhigh");
- Claude Code as a tool, such as how to install the skill.

## Working with Models

Each model lives in its own directory under `3d-models/` with a brief README explaining what it is.

### Record which AI model designed it

Every model README ends with a `## Design history` table recording which AI model produced each version, and which reviewed it:

```markdown
## Design history

| Version | AI model | Date | Change |
|---|---|---|---|
| v1 | claude-opus-5 | 2026-09-07 | Initial design |
| v2 | claude-opus-5-5 (final review: claude-fable-5-1) | 2026-09-26 | Thicker arm after v1 snapped at the hinge |
```

- Add a row whenever you create a design or change its geometry. Several changes by the same model to the same version can share one row; a different model touching that version gets its own row.
- Use the exact model ID you are running as, never a guessed marketing name. In Claude Code on the web, `get_session` reports it (`session_context.model` and `last_served_model`; if they differ, list both). If you can't determine it, write `unknown`.
- If a final review ran on another model, add it in brackets, as in the v2 row.
- When a README has no table yet, add one, but don't invent rows for earlier versions whose model you can't verify. Commits made before the attribution rule carry `Co-Authored-By: Claude …` trailers, and those count as verification.

## Git Workflow

Pushing directly to `main` is fine for this repo: no pull request or feature branch is needed, even if a session starts out on one.

- **On `main`:** confirm with the user before every push, follow-ups included. Commit locally, say what is going up, and wait for approval.
- **On a feature or PR branch:** push as normal, without asking. Don't create or merge a pull request unless the user asks for that.
